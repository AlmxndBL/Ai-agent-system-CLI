1บทสรุปผู้บริหาร

โปรเจคนี้ ออกแบบด้านความปลอดภัยมาดีเกินระดับทั่วไปมาก — ทุกการกระทำที่แก้ไขระบบ (write/edit/run_bash) ต้องผ่าน "approval gate" ที่บังคับใส่รหัส TOTP แบบ out-of-band ทุกครั้ง, มี kill-switch, audit log แบบ hash-chain, การแยก secret ออกจาก environment และการตรวจ path traversal ที่รอบคอบ. จุดแข็งเหล่านี้ทำให้ช่องโหว่จำนวนมากถูกลดความรุนแรงลง เพราะผู้โจมตีต้องผ่านการยืนยันตัวตนของเจ้าของก่อน.

อย่างไรก็ตาม การตรวจเชิงลึกพบจุดที่ยังต้องแก้ โดยเฉพาะ 2 จุดระดับ High ที่ verifier อิสระยืนยันแล้ว และจุดที่กระทบความถูกต้องของ audit log. รอบนี้ได้ ลงมือแก้จุดสำคัญไปแล้ว 3 จุด + เสริมความแข็งแรงอีก 1 จุด พร้อมเพิ่มเทสต์อัตโนมัติ.

4สิ่งที่แก้ไขแล้วในรอบนี้

แก้ไปแล้ว 4 จุด พร้อมเทสต์อัตโนมัติ (src/test-security.ts เพิ่มเป็น 12 เทสต์ ผ่านทั้งหมด, tsc --noEmit สะอาด).

HIGH H1 — ปิดช่อง TOCTOU / symlink write-escape

ปัญหา: validatePath() ถูกเรียกก่อน requestApproval() ที่บล็อกรอมนุษย์เป็นนาที แล้วค่อยเขียนไฟล์ — ระหว่างนั้นถ้า component ถูกสลับเป็น symlink การเขียนจะหลุดออกนอก workspace. ซ้ำร้าย กรณีไฟล์ยังไม่มี validatePath คืน path แบบ lexical (ไม่เคย canonicalize).

วิธีแก้: (1) ให้ validatePath anchor path ที่ยังไม่มีเข้ากับ realpath ของ ancestor จริง; (2) เพิ่ม assertNoSymlinkEscape() ที่ไล่ lstat ทุก component แล้วปฏิเสธถ้าเจอ symlink; (3) เรียก validate + assert ซ้ำหลัง approval ทันทีก่อนเขียนใน write_file/edit_file.

// tools/mutate.ts — writeFileTool (หลังผู้ใช้กด approve)
+ const safeTarget = await validatePath(userPath);          // re-validate ปิดช่อง TOCTOU
+ await assertNoSymlinkEscape(path.dirname(safeTarget));    // ปฏิเสธ symlink ในเส้นทาง
+ await fs.mkdir(path.dirname(safeTarget), { recursive:true });
+ await assertNoSymlinkEscape(safeTarget);
+ await fs.writeFile(safeTarget, content, 'utf8');
ยืนยันจริง: ทดสอบด้วย Windows junction แล้ว guard ปฏิเสธถูกต้อง — "escape" is a symlink — refusing to follow it out of the workspace. (หมายเหตุ: ยังเหลือ micro-window เล็กน้อยระดับ OS ที่ต้องปิดสมบูรณ์ด้วย openat-style fd — ระบุไว้เป็นงานต่อยอด)

HIGH H2 — TOTP: กัน brute-force และ replay

ปัญหา: verifyTotp ไม่จำกัดจำนวนครั้งเดา และรหัสที่ถูกต้องใช้ซ้ำได้ภายในหน้าต่าง ±90 วินาที — จุดนี้คือ "เกราะหลัก" ของ T2 (บัญชีถูกยึด).

วิธีแก้: เพิ่มมอดูล core/totp-guard.ts: (1) replay cache — รหัสใช้ได้ครั้งเดียวต่อ time-step; (2) lockout — ผิดครบ 5 ครั้งล็อกพร้อม backoff แบบทวีคูณ (1→2→4… สูงสุด 15 นาที); (3) เทียบรหัสด้วย crypto.timingSafeEqual. เชื่อมเข้ากับทุกจุดที่เรียก TOTP ใน telegram.ts/discord.ts (ทั้ง approval และ /unpanic).

// telegram.ts / discord.ts
- const ok = verifyTotp(content, totpSecret);
+ const res = verifyTotpGuarded(`telegram-${chatId}`, content, totpSecret);
//  res.reason = 'locked' | 'replay' | 'invalid' → ตอบผู้ใช้ต่างกัน

MED M1 — Audit log: กัน race ตอนเขียนพร้อมกัน

ปัญหา: logAudit() อ่าน entry สุดท้าย → คำนวณ index/prevHash → append โดยไม่มี lock. เมื่อ tool หลายตัว/หลายแชตเขียน audit.log พร้อมกัน จะได้ index ซ้ำ → verifyAuditChain แจ้ง "TAMPERED" หลอก.

วิธีแก้: serialize ทุก append ด้วย promise-chain ระดับมอดูล ให้เขียนทีละรายการแบบ atomic ต่อโปรเซส.

+ let writeChain = Promise.resolve();
  export async function logAudit(...) {
+   const run = writeChain.then(() => appendEntry(sessionId, action, details));
+   writeChain = run.catch(() => undefined);   // ไม่ให้ error ตัวเดียวค้างทั้งคิว
+   return run;
  }

เทสต์ใหม่: ยิง logAudit 25 ครั้งพร้อมกันด้วย Promise.all แล้ว verifyAuditChain() ยัง valid ครบ 25 รายการ.

MED M2 — Audit chain: เสริม HMAC keying

ปัญหา: chain ใช้ SHA-256 บน field สาธารณะล้วน → ผู้เขียนไฟล์ได้คำนวณ chain ใหม่ทั้งเส้นหลังแก้ (ปลอมผ่าน verify).

วิธีแก้: ถ้าตั้ง AUDIT_HMAC_KEY (ผ่าน secret broker) จะ key chain ด้วย HMAC-SHA256 — ปลอมไม่ได้ถ้าไม่มีคีย์; ถ้าไม่ตั้งจะ fallback เป็น SHA-256 เดิม (backward-compatible). แนะนำตั้งคีย์นี้บน deployment จริง.

5รายละเอียดช่องโหว่ที่ยังเหลือ (แนะนำให้แก้ต่อ)

M3 Secret scrubbing เป็น allowlist ผิดด้าน MED

ไฟล์: core/secrets.ts:50-56 · ประเภท: secret leakage (T4)

getSafeChildEnv() ลบเฉพาะคีย์ใน SENSITIVE_KEYS ที่ hardcode. Secret อื่นที่มีในเครื่อง (OPENAI_API_KEY, AWS_*, GitHub token ฯลฯ) จะหลุดเข้าสู่ child process ของ run_bash. สถานการณ์: เจ้าของมี AWS_SECRET_ACCESS_KEY ใน environment → agent รัน npm run build ที่มี postbuild อ่าน env → คีย์รั่ว.

แนะนำ: เปลี่ยนเป็น deny-by-default — ส่งเฉพาะ env ที่ allowlist (PATH, HOME, SystemRoot…) ให้ child แทนการ copy ทั้ง process.env แล้วลบทีละคีย์; หรือ regex คลุม *_KEY|*_TOKEN|*_SECRET.

M4 Session lock / permission ไม่ตรงกับที่ออกแบบ MED

ไฟล์: core/session.ts · ประเภท: concurrency + info disclosure

เอกสารระบุ "optimistic-lock counter" และ chmod 600 แต่โค้ดมีแค่ lock ในหน่วยความจำ (ไม่มี cross-process), ไม่มี version field, ไม่ตั้ง permission. สถานการณ์: รัน telegram + discord พร้อมกัน (คนละโปรเซส) บนเซสชันเดียว → เขียนไฟล์ทับกัน = lost update; ไฟล์บทสนทนาเต็มถูกเขียนแบบ world-readable (0644) บนเครื่อง multi-user.

แนะนำ: ใช้ file lock ข้ามโปรเซส (เช่น lockfile .lock + O_EXCL), เพิ่ม version ใน session แล้ว compare-and-swap ตอน save, และ fs.writeFile(path, data, { mode: 0o600 }).

M5 ไม่มี cost/token budget และ rate limiting MED

ไฟล์: core/agent.ts, gateway · ประเภท: abuse / cost DoS

stepCountIs(10) จำกัดแค่จำนวน step ต่อเทิร์น ไม่มีเพดานจำนวนเทิร์นต่อวัน, token, หรือค่าใช้จ่าย API. prompt ที่วนลูปหรือถูกสแปมเผาเครดิตได้เรื่อย ๆ ("rate-limit layer" ในเอกสารไม่มีในโค้ด).

แนะนำ: เพิ่ม budget guard นับ token/ราคาโดยประมาณต่อวัน + จำกัดข้อความต่อนาทีต่อผู้ใช้ + คำสั่ง /budget ดูยอด.

M6 คำสั่งใน allowlist ยังรันโค้ดของ repo MED

ไฟล์: tools/mutate.ts:64-107 · ประเภท: confused deputy (T6)

npm run build / npm test รัน script ใน package.json (โค้ดอะไรก็ได้; --ignore-scripts กันแค่ lifecycle hook ไม่กัน build/test เอง) และ git status/commit ทริกเกอร์ git hook หรือ !-alias ใน .git/config ของ repo ได้. ป๊อปอัพ approval โชว์ "npm run build" ดูไม่มีพิษ แต่รันโค้ดผู้โจมตีถ้า repo ไม่น่าเชื่อถือ.

แนะนำ: ให้ approval prompt แสดง "ผลจริง" เช่น เนื้อหา script ที่จะรัน; พิจารณา git -c core.hooksPath=/dev/null และเตือนเมื่อ repo มี alias แบบ !.

M7 Windows .cmd injection MED

tools/mutate.ts:18-25

เรียก npm.cmd/tsc.cmd/npx.cmd ผ่าน execFile; บน Node ที่ยังไม่แพตช์ (<18.20.2/<20.12.2) args ที่มี metachar หลุดผ่าน cmd.exe ได้. แนะนำ: ตรึงเวอร์ชัน Node ขั้นต่ำใน engines + sanitize args.

M8 hardening ตรวจแค่ admin/root MED

core/hardening.ts

รันด้วยบัญชีปกติของเจ้าของจะขึ้น "Privilege check OK" ทั้งที่ยังเข้าถึง ~/.ssh, browser profile ได้ (เป้า T10). แนะนำ: ตรวจว่าเป็น dedicated service user จริง หรือบังคับ container.

ระดับ Low / คุณภาพโค้ด

  • L1 grep (tools/index.ts) อ่านทุกไฟล์เต็ม ไม่มี cap ขนาด/จำนวน — โมเดลสั่ง DoS ได้. แนะนำ cap ต่อไฟล์ + จำนวนไฟล์รวม.
  • L2 globToRegex เสี่ยง ReDoS จาก **→.*. แนะนำจำกัดความยาว pattern / ใช้ตัวจับคู่ที่ปลอดภัย.
  • L3 taint ใช้ 9 สตริงอังกฤษ hardcode เลี่ยงง่าย + หายเมื่อ restart (เป็นแค่ advisory เพราะ approval คือ gate จริง).
  • L4 Telegram "fallback" retry ข้อความ markdown เดิมที่เพิ่ง fail — ควร strip markdown แล้วส่ง plain.
  • L5 /model เขียน process.env.MODEL_PROVIDER เป็น global แชร์ทุกแชต — ควรเก็บ provider ระดับเซสชัน.
  • L6 loadSession JSON.parse ไม่มี schema — ควร validate ด้วย zod.
  • L7 heartbeat file ไม่มี auth — โปรเซสอื่นในเครื่อง spoof/ลบได้.
  • L8 supervisor spawn(shell:true) บน Windows — args เป็นภายใน แต่เป็น smell ควรเลี่ยง.

  • Config validation: ตรวจ .env ด้วย zod ตอน startup แจ้ง error ชัดถ้าตั้งค่าผิด.

7แผนการทดสอบ (Testing Strategy)

สถานะปัจจุบัน: มีแค่ src/test-security.ts (harness เขียนเอง) + smoke test ของ provider — ไม่มี test framework, ไม่มี npm test, ไม่มี coverage, ไม่มี CI, coverage ประเมิน ~15–20%. รอบนี้เพิ่มเทสต์ในสไตล์ harness เดิมสำหรับจุดที่แก้ (รวมเป็น 12 เทสต์ ผ่านหมด) และแนะนำเส้นทางยกระดับดังนี้.

Testing Pyramid ที่แนะนำ

        ╱   E2E   ╲        น้อย — daemon จริง + bot จำลอง (สั่ง→approve→ผลลัพธ์)
      ╱ Integration ╲      กลาง — agent loop, tool + approval, session I/O
    ╱   Unit Tests    ╲    เยอะ — allowlist, path, totp, audit, taint, compaction

เครื่องมือที่แนะนำ

Vitest (native TypeScript, เร็ว, มี coverage v8 ในตัว) + สคริปต์ "test": "vitest run --coverage" ใน package.json. ตั้ง coverage gate เริ่มต้นที่ core modules 80%. เพิ่ม GitHub Actions รัน typecheck + test + coverage ทุก push/PR.
